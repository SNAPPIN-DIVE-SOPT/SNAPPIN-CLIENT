# 도메인 지식이 있는 코드는 반복돼도 공용화하지 않는다

`apps/web/src/ui`를 `product`/`portfolio` 도메인 폴더로 재편하면서, 두 도메인 모두 "좋아요 토글" 상태 훅과 "좋아요 API 호출" 훅을 구조적으로 똑같이 필요로 했다. 이걸 하나의 공용 훅으로 묶어 `ui/` 루트나 별도 공용 위치에 두지 않고, 각 도메인(`product/preview`, `portfolio/preview`) 안에 독립적으로 선언해 `useProductLikeButton`/`usePortfolioLikeButton`, `useWishProductLike`/`useWishPortfolioLike`로 분리했다. 코드가 반복된다는 사실이 곧 "공통"임을 의미하지 않기 때문이다 — 이 로직은 겉보기엔 범용적이어 보이지만 "무엇에 대한 좋아요인지"라는 도메인 지식을 갖고 있고, 공용 위치로 올리는 순간 그 위치가 두 도메인을 모두 알아야 하게 되어 한쪽 도메인의 변화가 다른 도메인까지 흔드는 결합이 생긴다.

## Considered Options

- **하나의 공용 `useLikeButton` 훅으로 통합**: 두 도메인이 지금은 우연히 비슷해 보일 뿐, `product`/`portfolio`가 각자 다르게 진화할 수 있는 지점(도메인 지식)을 하나의 구현으로 묶으면, 한쪽 요구사항 변경(예: `product`만 좋아요 실패 시 토스트 문구를 다르게 바꾸는 경우)이 다른 도메인 코드까지 재검토하게 만드는 결합이 생긴다. 기각.
- **도메인별로 각자 소유** (채택): 지금은 코드가 중복되지만, 각 도메인이 서로의 사정을 몰라도 독립적으로 진화할 수 있다. 실제로 완전히 동일하게 유지된다는 게 여러 차례 확인되면 그때 도메인 무관 형태로 추출한다.

## Consequences

- `useProductLikeButton`/`usePortfolioLikeButton`, `useWishProductLike`/`useWishPortfolioLike` 코드가 당분간 거의 동일하게 중복된다. 의도된 것이며, 리뷰에서 "중복이니 합치자"는 지적이 나오면 이 ADR을 참조한다.
- 앞으로 다른 도메인 폴더(`apps/web/src/ui/**`)에서 비슷한 요구가 생겨도, 그 로직이 도메인 지식을 갖고 있다면 같은 패턴(도메인 로컬 소유)을 따르고 미리 공용화하지 않는다. 판단 기준은 "도메인 지식 없이도 이해되는 코드인가" — 포맷팅 함수나 순수 유틸처럼 어떤 도메인인지 몰라도 되는 코드만 공용 후보다.
