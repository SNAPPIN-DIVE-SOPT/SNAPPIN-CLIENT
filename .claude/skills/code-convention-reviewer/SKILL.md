# Code Reviewer

이 프로젝트(snappin-client)의 팀 컨벤션 준수 여부만 리뷰합니다. **"우리 팀 규칙대로 작성됐는가"**가 유일한 관심사입니다 — 버그, 프레임워크 모범 사례, git 컨벤션은 다루지 않습니다 (각각 `bug-reviewer`, `next-best-practices`/`react-vercel-performance`, `git-convention-checker` 스킬 참고).

## 컨벤션 기준

`references/conventions.md` (이 스킬 폴더 안)를 읽으세요. 이 프로젝트의 코드 컨벤션을 담은 유일한 기준 문서입니다.

## 리뷰 절차

1. **리뷰 대상 파악**
   - 사용자가 특정 파일을 지정하면 그 파일만 본다.
   - 지정하지 않았다면 현재 브랜치와 베이스 브랜치(보통 `develop`, 없으면 `main`) 사이의 diff를 본다. `git merge-base`로 실제로 갈라진 지점을 찾아서 그 이후 변경분만 본다 — 남의 커밋까지 걸리지 않도록 주의.

2. **컨벤션 문서 읽기**

3. **컨벤션 체크**
   - diff에 포함된 변경 라인 위주로, 각 파일을 훑으며 컨벤션 위반을 찾는다.
   - 위반을 찾으면 파일 경로와 라인 번호, 어떤 규칙을 어겼는지, 어떻게 고치면 되는지를 구체적으로 적는다. 애매한 스타일 취향이 아니라 문서에 명시된 규칙에 근거해서만 지적한다.
   - 심각도를 둘로 나눈다:
     - **필수 수정**: 명확히 금지되거나 강제되는 규칙 위반 (예: `var` 사용, 의미 없는 변수명, `button`에 `type` 누락, key로 index 사용, 문자열을 `+`로 연결, switch에서 break 누락, 주석을 코드 아래에 작성)
     - **권장 수정**: 기본 원칙이지만 예외가 허용되는 규칙 (예: 삼항 연산자 대신 if-else 사용했지만 중첩이 심해 오히려 가독성이 나은 경우, 구조분해할당을 안 쓴 경우 등). 애매하면 왜 권장으로 분류했는지 짧게 판단 근거를 남긴다.

4. **결과 정리** — 아래 "출력 형식"대로 작성한다.

5. **수정 여부 확인 후 적용** — 위반이 하나라도 있으면, 결과를 보여준 다음 고쳐도 될지 물어본다. 사용자가 승인하면 위반 항목들을 컨벤션에 맞게 직접 수정하고, 어떤 파일을 어떻게 고쳤는지 간단히 요약한다. 승인 전에는 코드를 건드리지 않는다.

## 출력 형식

```markdown
# 컨벤션 리뷰 결과

## 필수 수정
- `경로/파일.tsx:12` — var 사용 금지. const로 바꾸세요.
- ...

## 권장 수정
- `경로/파일.tsx:30` — 조건문은 삼항 연산자 권장. 다만 중첩이 있어 현재 형태도 무방할 수 있음.
- ...

## 요약
필수 수정 N건, 권장 수정 M건
```

위반이 하나도 없으면 축하 인사 없이 "필수 수정 0건, 권장 수정 0건"이라고 짧게 요약하고 끝낸다. 과장하거나 억지로 지적거리를 만들지 않는다.
