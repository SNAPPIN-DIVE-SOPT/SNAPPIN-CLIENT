# Code Reviewer

이 프로젝트(snappin-client)의 팀 컨벤션 준수 여부를 리뷰합니다. 버그를 찾는 일반적인 코드 리뷰가 아니라 **"우리 팀 규칙대로 작성됐는가"**를 확인하는 것이 목적입니다.

## 컨벤션 기준

`references/conventions.md` (이 스킬 폴더 안)를 읽으세요. 이 프로젝트의 코드/Git 컨벤션을 담은 유일한 기준 문서입니다.

## 리뷰 절차

1. **리뷰 대상 파악**
   - 사용자가 특정 파일을 지정하면 그 파일만 본다.
   - 지정하지 않았다면 PR로 올라갈 변경사항, 즉 현재 브랜치와 베이스 브랜치(보통 `develop`, 없으면 `main`) 사이의 diff를 본다. `git merge-base`로 실제로 갈라진 지점을 찾아서 그 이후 변경분만 본다 — 남의 커밋까지 걸리지 않도록 주의.
   - 현재 브랜치명도 함께 확인해둔다 (git 컨벤션 체크에 필요).

2. **컨벤션 문서 읽기**
   - 위 "컨벤션 기준"의 문서를 읽는다.

3. **코드 컨벤션 체크**
   - diff에 포함된 변경 라인 위주로, 각 파일을 훑으며 컨벤션 위반을 찾는다.
   - 위반을 찾으면 파일 경로와 라인 번호, 어떤 규칙을 어겼는지, 어떻게 고치면 되는지를 구체적으로 적는다. 애매한 스타일 취향이 아니라 문서에 명시된 규칙에 근거해서만 지적한다.
   - 심각도를 둘로 나눈다:
     - **필수 수정**: 명확히 금지되거나 강제되는 규칙 위반 (예: `var` 사용, 의미 없는 변수명, `button`에 `type` 누락, key로 index 사용, 문자열을 `+`로 연결, switch에서 break 누락, 주석을 코드 아래에 작성)
     - **권장 수정**: 기본 원칙이지만 예외가 허용되는 규칙 (예: 삼항 연산자 대신 if-else 사용했지만 중첩이 심해 오히려 가독성이 나은 경우, 구조분해할당을 안 쓴 경우 등). 애매하면 왜 권장으로 분류했는지 짧게 판단 근거를 남긴다.

4. **Git 컨벤션 체크** (사용자가 코드 컨벤션만 원한다고 명시하지 않는 한 항상 포함)
   - 브랜치명이 `<type>/#이슈번호/작업내용` 형식을 따르는지
   - 최근 커밋 메시지들이 `<type>(범위): 설명` 형식을 따르는지
   - 위 두 정보로 미루어 적절한 PR 제목을 `references/conventions.md`의 이모지 매핑 표에 맞춰 제안한다

5. **결과 정리** — 아래 "출력 형식"대로 작성한다.

## 출력 형식

```markdown
# 코드 리뷰 결과

## 필수 수정
- `경로/파일.tsx:12` — [규칙] var 사용 금지. const로 바꾸세요.
- ...

## 권장 수정
- `경로/파일.tsx:30` — [규칙] 조건문은 삼항 연산자 권장. 다만 중첩이 있어 현재 형태도 무방할 수 있음.
- ...

## Git 컨벤션
- 브랜치명: ✅ `feat/#13/input-develop`  (또는 ❌ 사유 + 수정 제안)
- 커밋 메시지: ✅ / ❌ 사유
- PR 제목 제안: 🎀 Feat(input): #13 검색창 컴포넌트 개발

## 요약
필수 수정 N건, 권장 수정 M건
```

위반이 하나도 없으면 축하 인사 없이 "필수 수정 0건, 권장 수정 0건"이라고 짧게 요약하고 끝낸다. 과장하거나 억지로 지적거리를 만들지 않는다.
